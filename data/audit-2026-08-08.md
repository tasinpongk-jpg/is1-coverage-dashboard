## Detailed findings

### #1 + #2: Deployed dashboard stale 56 days; vault rebuild missing from CI

**This is the same root cause.** Two angles:

1. **CI side**: `daily.yml` line 263–291 builds morning-brief, sector-heatmap, unusual-trading, disclosure-pulse — but never calls `python scripts/build_vault_ticker_notes.py`. The vault snapshot only gets refreshed by the local Windows task `IS1-Vault-Refresh` (`SYSTEM.md` line 153), which is `IS1-Vault-Refresh | Daily 10:30 BKK | Pulls R2 DB → patches Obsidian` — **but that's the wrong direction** (it pulls from R2, it doesn't push `vault-ticker-notes.json`). Looking at `SYSTEM.md` more carefully: the task updates Obsidian vault notes FROM R2, not the dashboard JSON FROM vault. So **nothing in the system ever rebuilds `data/vault-ticker-notes.json` on a schedule.**
2. **Host side**: `schtasks /query /fo LIST | grep IS1` returns empty — the Windows task doesn't exist on this machine. So the dashboard stays stale forever unless someone manually runs the script.

**Falsifier for fix #1:** "Adding the step to CI is the wrong fix" — counter: if the vault is on OneDrive on the user's laptop, CI can't read it. **This is true.** Vault root is `~/OneDrive - The Stock Exchange of Thailand/Claude-Vault/...`, which is not in CI. So CI cannot rebuild. The actual fix is:
   - (a) Push vault markdown files into the repo (or to R2), so CI has them; OR
   - (b) Rebuild `vault-ticker-notes.json` locally on the laptop and commit it; OR
   - (c) Use the existing Cloudflare Worker cron (already mentioned in `README.md` as the "reliable primary scheduler") to read the vault via a sync.

**Recommended fix (lowest risk):** (b) — add a small bash script that runs `build_vault_ticker_notes.py` then `git add data/vault-ticker-notes.json && git commit && git push`, register it as Windows task. This mirrors what the other 4 daily builds already do (just locally instead of in CI).

### #3: Tests fail with missing duckdb

```
python tests/test_form59.py
  File "...\test_form59.py", line 7, in <module>
    import duckdb
ModuleNotFoundError: No module named 'duckdb'
```

`requirements.txt` line 9 pins `duckdb==1.5.2`, but the **system Python 3.14 used by `python` is `PythonSoftwareFoundation.PythonManager_26.3.240.0`**, NOT the venv at `~/AppData/Local/hermes/hermes-agent/venv/`. The system Python has no site-packages. So `python tests/test_*.py` runs against the wrong interpreter.

**Fix:** Either use `python -m pytest` from the venv, or document that tests need `pip install -r requirements.txt` first. The Hermes CI (`daily.yml` line 132) uses `pip install -r requirements.txt` then `python scripts/build_daily.py` — which is fine because the GitHub Actions runner is fresh. But local testing is broken.

### #4: sec-form59.json is empty

```json
{
  "asOf": "2026-08-06",
  "windowDays": 90,
  "total": 0,
  "bySide": {"buy": 0, "sell": 0, "transfer": 0, "other": 0},
  "netNotional": 0.0,
  "tickers": [],
  "items": [],
  "_built_at": "2026-08-06T05:47:37+00:00"
}
```

**Falsifier:** "SEC just had no Form 59 filings for 90 days" — false, the SEC iDisc page has filings daily. Either:
- The Playwright Chromium scrape silently failed (`daily.yml` line 109: `continue-on-error: true` on `python -m playwright install --with-deps chromium`),
- `external_sources.py` Form 59 path returned empty due to a SEC WAF change,
- Or the proxy is down and we lost the warning.

**Real impact:** The ⚡ Hermes agent uses `sec-form59` per `README.md` line 44 — so the "silent filers / Form 59 trades" signal is dead for the user.
